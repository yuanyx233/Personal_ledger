# Self-hosting Personal Ledger

This guide takes you from an empty Cloudflare account to your own running ledger. It assumes no knowledge of this project and refers to no resource belonging to anyone else's deployment.

You will end up with one Worker serving both the API and the frontend, one D1 database holding your entries, and Cloudflare Access in front of everything.

## What you need first

- **A Cloudflare account.** The free plan is enough: Workers, D1 and Zero Trust all have free tiers that comfortably fit one person's ledger.
- **Node.js 24.17.0 and npm 11.11.1.** The versions are pinned in `.nvmrc` and `package.json`; other versions may work but are not what the test suite runs against.
- **An email address you control.** It becomes the only identity allowed to read your ledger.

### Cloudflare Access is required, not optional

The Worker authenticates by verifying a Cloudflare Access JWT and comparing its email claim to a single owner address. There is no password form, no session table, and **no fallback authentication**. If you deploy the Worker without putting Access in front of it, your ledger is open to anyone who finds the URL.

Set up Access before you deploy, not after.

## 1. Get the code and install

```bash
git clone https://github.com/yuanyx233/Personal_ledger.git
cd Personal_ledger
npm ci
```

## 2. Create your database

```bash
npx wrangler d1 create personal-ledger-production
```

The command prints a `database_id`. Open `apps/web/wrangler.jsonc` and replace the placeholder:

```jsonc
"database_id": "REPLACE_ME_D1_DATABASE_ID",
```

Deploying without replacing it fails with `Invalid property: databaseId => Invalid uuid`, which names the unreplaced value.

Apply the schema:

```bash
npx wrangler d1 migrations apply DB --remote --config apps/web/wrangler.jsonc
```

## 3. Set up Cloudflare Access

In the Cloudflare dashboard, under **Zero Trust**:

1. Note your **team domain** — `https://<your-team>.cloudflareaccess.com`. This is `ACCESS_TEAM_DOMAIN`. The Worker fetches signing keys from `/cdn-cgi/access/certs` on it, and requires the value to match `https://<name>.cloudflareaccess.com` exactly.
2. Create a **self-hosted application** pointing at the hostname your Worker will serve.
3. Add **one Allow policy** matching exactly your own email address. Do not add a Bypass policy or a broader rule — a Bypass policy that matches first would let requests reach the Worker without an assertion.
4. Open the application's settings and copy its **Application Audience (AUD) tag**. This is `ACCESS_AUD`.

## 4. Set the Worker secrets

Four secrets are required. Set each one:

```bash
npx wrangler secret put ACCESS_AUD --config apps/web/wrangler.jsonc
npx wrangler secret put ACCESS_TEAM_DOMAIN --config apps/web/wrangler.jsonc
npx wrangler secret put OWNER_EMAIL --config apps/web/wrangler.jsonc
npx wrangler secret put CSRF_HMAC_KEY --config apps/web/wrangler.jsonc
```

| Secret               | Where it comes from              | Format the Worker requires                                         |
| -------------------- | -------------------------------- | ------------------------------------------------------------------ |
| `ACCESS_AUD`         | The Access application's AUD tag | At least 8 characters, and not left as a `REPLACE_ME_` placeholder |
| `ACCESS_TEAM_DOMAIN` | Your Zero Trust team domain      | `https://<team>.cloudflareaccess.com`                              |
| `OWNER_EMAIL`        | The address in your Allow policy | A valid email address                                              |
| `CSRF_HMAC_KEY`      | Generated by you, see below      | 32 random bytes, Base64, which is 43 characters and a trailing `=` |

Generate the CSRF key:

```bash
node -e "console.log(require('node:crypto').randomBytes(32).toString('base64'))"
```

Keep it out of shell history files, source control, URLs and logs. It is not recoverable from the deployment; losing it means issuing a new one, which invalidates open sessions.

## 5. Configure your region and currencies

Two values describe where your ledger lives. They are **public configuration**, embedded in the browser bundle — never put secrets in them.

Create `apps/web/.env` by copying the example:

```bash
cp apps/web/.env.example apps/web/.env
```

Then edit both halves so they agree:

| Setting                                     | Where   | Meaning                                     |
| ------------------------------------------- | ------- | ------------------------------------------- |
| `VITE_APP_TIMEZONE` in `apps/web/.env`      | Browser | The calendar the interface computes days in |
| `APP_TIMEZONE` in `apps/web/wrangler.jsonc` | Worker  | The calendar the server computes days in    |
| `VITE_LEDGER_CURRENCIES` in `apps/web/.env` | Browser | Which currencies the entry controls offer   |

**The two timezone values must name the same zone.** Each half computes calendar days on its own, so a disagreement would file an entry under one day in the browser and another in storage. The application detects the mismatch and refuses to run rather than letting the two drift.

Use a named IANA zone such as `Europe/Berlin` or `Asia/Shanghai`. A fixed offset like `+05:00` is rejected: it cannot express daylight saving, and your month boundaries would be wrong for half the year.

### Which currencies to list

`VITE_LEDGER_CURRENCIES` is the set of currencies **your accounts are denominated in** — usually one, sometimes two. It is not a list of currencies you might encounter. Cross-border spending arrives on your statement already converted by your card issuer, so a trip abroad does not need its own currency here.

### Currencies that are not supported

Amounts are stored as whole minor units at a fixed ratio of 1/100. Currencies whose ISO 4217 minor unit is not one hundredth are rejected, because storing them at this scale would silently record the wrong amount:

- **No minor unit**: JPY, KRW, VND, ISK, CLP, XAF, XOF, XPF and others.
- **Three decimals**: BHD, IQD, JOD, KWD, LYD, OMR, TND.
- **Four decimals**: CLF, UYW.

Every other three-letter code is accepted, including EUR, GBP, CNY, AUD, CHF and INR.

## 6. Deploy

```bash
npm run verify
npm run build
npx wrangler deploy --config apps/web/wrangler.jsonc
```

`npm run verify` runs formatting, lint, type checks, the full test suite with coverage thresholds, browser tests and a production build. It is worth running before your first deployment so a broken local setup surfaces here rather than in production.

The Worker declares one Cron Trigger, `*/15 * * * *`, which posts due subscription charges. Cloudflare replaces a Worker's schedules with whatever the configuration declares, so keep that value in `triggers.crons` — removing it silently stops subscriptions from posting.

## 7. Check that it works

Two checks, in this order:

1. **Anonymous requests are denied.** Open your Worker's URL in a private window. Cloudflare Access should challenge you before any ledger data is served. If you see the ledger without signing in, stop and fix your Access policy before entering real data.
2. **You can sign in.** Sign in with the email in your Allow policy. The overview should load, and Settings should offer the interface language control.

Then record one entry by hand and confirm it appears in Transactions with the date you expect — that exercises the timezone configuration end to end.

## Categories in your language

The default categories (`Food & Dining`, `Housing`, `Transportation` and so on) are seeded in English and are **editable**. Rename them to whatever you like from the interface; the application will never overwrite your names with a translation.

Only the two immutable system categories, Transfer and Unclassified, follow the interface language, because you cannot rename them.

## Backups

Download a full JSON backup from Settings. CSV export is convenient for reading but is not a backup — it does not carry everything needed to restore.

To restore into a fresh local database:

```bash
npm run db:restore -- --input ./ledger-export.json --persist-to /tmp/ledger-restored-d1
```

Restoring refuses to proceed when the backup's recorded timezone differs from the instance it is being restored into, because the stored dates were computed in the backup's zone. Pass `--timezone <zone>` when you are deliberately moving a ledger between zones.

## Keeping up to date

```bash
git pull
npm ci
npm run verify
npm run build
npx wrangler deploy --config apps/web/wrangler.jsonc
```

Check whether `migrations/` gained new files; if so, apply them before deploying. Database migrations are additive and are never reversed automatically.
