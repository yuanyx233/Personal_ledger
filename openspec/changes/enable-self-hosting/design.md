## Context

账本目前是单所有者、单部署、单地区的应用。鉴权由 Cloudflare Access 签发 JWT、Worker 验签后比对单个 `OWNER_EMAIL` 完成（`apps/web/worker/security/access.ts`）。数据库没有 `user_id` 列，17 张表共享一个所有者的数据。

所有者选择的方向是**开源自托管**而非多租户：每个使用者部署自己的 Worker、D1 与 Access，数据隔离由部署边界而非应用逻辑保证。这使鉴权与数据模型完全不必改动 —— 本变更的全部工作集中在"让一个陌生人能够部署并在自己的地区、自己的语言下使用"。

现状盘点（本次探索实测）：

| 项 | 现状 |
| --- | --- |
| 许可证 | 无 —— 法律上禁止 fork |
| 部署文档 | 所有者运维日志：含生产 version ID、资产哈希、授权措辞 |
| `wrangler.jsonc` | 写死生产 `database_id` |
| 时区 | `z.literal("America/Toronto")`，源码 9 处 |
| 货币 | `z.enum(["CAD","USD"])`，但**数据库约束已是通用的** `length(currency)=3 AND currency=upper(currency)` |
| 次要单位 | `/100` 与 `.toFixed(2)` 散布 10+ 处 |
| 界面语言 | `apps/web/src` 31 个文件 / 434 行硬编码中文；后端、domain、persistence、migrations **零中文** |
| 运行时依赖 | `@ledger/domain`、`@ledger/persistence`、`jose`、`react`、`react-dom` —— 共 5 个 |

## Goals / Non-Goals

**Goals:**

- 让一个没有本项目背景的人，按一份文档从零部署出可用实例。
- 让时区与货币成为部署配置，而不是编译期常量。
- 让界面在中英之间切换，且不遗留硬编码字面量。
- 保持现有所有者实例的行为、数据与备份完全不变。

**Non-Goals:**

- 多租户、账号密码、注册流程、会话存储 —— 明确不做，Access 继续是唯一鉴权。
- 支持次要单位不是 1/100 的货币（JPY、KRW、KWD 等）。
- 汇率换算或跨币种合并 —— 报表继续按币种分列。
- 后端与领域层的本地化：这两层当前零用户可见字符串，错误码保持机器可读标识。
- 公开仓库与部署本身 —— 均需另行明确授权。

## Decisions

### D1. 许可证选 MIT —— 已由所有者确认

**选择**：MIT。所有者于 2026-09-21 确认。

**理由**：目标是"别人能自己跑起来"，MIT 的许可范围最宽、文本最短、对自托管者零负担，且与仓库已有的 Cloudflare/React 生态惯例一致。其免责声明是本项目（金融类应用）真正需要的部分。

**已放弃的备选**：Apache-2.0 增加专利授权与变更声明义务；AGPL-3.0 的第 13 条网络条款是唯一能约束"他人做成闭源托管服务"的主流选项，且对自托管者本身零义务 —— 所有者评估该场景概率过低，不值得为此牺牲简洁性与生态兼容性。

**不可逆性**：已按 MIT 发布的版本，其授权永久有效。所有者作为版权持有人仍可对未来版本改换或增加许可。

### D2. i18n 自建，不引入依赖

**选择**：类型化字符串目录 + React Context，不引入 `react-i18next` 或同类库。

**理由**：应用只有 5 个运行时依赖、26 个组件、无路由库、无状态库；整个 `apps/web/src` 目前没有任何 `createContext` 调用。引入一个完整 i18n 框架（复数规则、命名空间、懒加载、插值 DSL）远超需要，且会成为自托管者必须理解的额外概念。

**目录完整性用类型保证**：

```ts
type TranslationKey = keyof typeof zhCN;
const en: Record<TranslationKey, string> = { ... };
```

缺键即 `tsc` 失败，满足 spec 的"目录完整性被强制"要求，无需额外测试。

**备选**：`react-i18next` 生态成熟、支持复数与 ICU 消息格式。若将来需要第三种语言或复杂复数规则，迁移成本低于现在就引入的持续成本。

### D3. 时区保留双变量，在既有 bootstrap 契约上做一致性校验

**选择**：保留 `VITE_APP_TIMEZONE`（编译期注入前端）与 `APP_TIMEZONE`（Worker 运行期 var）两个变量，各自从 `z.literal` 放宽为"经校验的 IANA 标识符"，并在前端启动时比对 Worker 返回值。

**校验方式**：`new Intl.DateTimeFormat(undefined, { timeZone: value })` 捕获 `RangeError`。不使用 `Intl.supportedValuesOf("timeZone")` —— 它在 workerd 与旧浏览器上的可用性不如前者稳定，且构造函数路径同时验证了实际会被使用的能力。

**一致性校验落点**：`api-contracts.ts:98` 的 bootstrap 响应已经携带 `timezone` 字段。前端拿到后与自身编译期值比对，不一致则渲染阻断式错误而非继续工作。这复用了现有契约，不新增端点。

**备选**：单一运行期变量、前端一律从 bootstrap 读取。更不易配错，但前端在拿到响应前无法做任何日期计算，会改变首屏逻辑；且编译期值消失后 `vite-env.d.ts` 的类型收窄能力也随之消失。取其次：保留双变量 + 显式校验。

### D4. 备份保持 `schemaVersion: 5`，放宽字段而非升版本

**选择**：`full-json-export.ts` 中 `timezone` 与 `currency` 从字面量/枚举放宽为校验过的字符串，**版本号仍为 5**。

**理由**：

- 变更前产出的 v5 备份（时区恒为 `America/Toronto`）在放宽后的校验下依然通过 —— 向后兼容天然成立，无需迁移分支。
- 升到 v6 会迫使恢复路径同时处理 v5 与 v6，并牵动 `remote-migration-guard` 与 README 中对版本号的既有承诺，换来的收益为零。
- `openspec/changes/.../restore-monthly-subscriptions` 已确立"v4 及更早不被接受"的边界，保持 v5 不动可维持该边界的稳定。

**代价**：柏林实例产出的 v5 备份无法被本变更之前的代码读取 —— 会得到一个字段校验错误而非清晰的版本错误。由于变更前的代码只存在于所有者自己的实例上，且该实例的时区不变，此风险在实践中不会发生。

**互斥校验**：恢复时若备份记录的时区与当前实例配置不同，在写入前报告给操作者（spec 已要求）。原因是库中所有日期都是在备份那个时区下算出来的，静默接受会让月份边界整体错位。

### D5. 货币用"非两位小数黑名单"而非"两位小数白名单"

**选择**：格式校验（三位大写字母）+ 显式拒绝已知的零位与三位小数 ISO 4217 代码。

**理由**：需要防的是**静默的标度错误**，不是拼写错误。

```
JPY 走 /100  →  ¥1000 显示成 ¥10.00   静默错 100 倍   ← 必须拦
XYZ（不存在）→  自成一个货币桶          所有者立刻看见   ← 无需拦
```

白名单需要维护 ~150 个代码，且其失败模式（合法货币被拦）比黑名单的失败模式（虚构代码被放行）更常见也更烦人。黑名单只需覆盖约 20 个例外，且精确命中了唯一危险的情况。

**备选**：完整 ISO 4217 白名单附小数位数表。若将来真要支持 JPY，这张表本来就是前置条件 —— 届时黑名单自然升级为白名单。

### D6. 分类名不在运行时翻译，改为安装时播种

**这是本次设计中唯一推翻了初始假设的决定。**

初始假设是"按 `system_key` 翻译内置分类"。实测 `migrations/0008_category_taxonomy.sql` 后发现该假设不成立：

```
category-expense-food     'Food & Dining'  system_key = NULL  editable = 1   ← 可被所有者改名
category-system-transfer  'Transfer'       system_key = 'TRANSFER'  editable = 0
```

7 个默认分类的 `system_key` 是 `NULL` 且**可编辑**，与所有者自建分类在数据上无法区分（只有固定 `id` 不同）。按 `id` 翻译会在所有者把 `Food & Dining` 改名为「餐饮」之后，用翻译覆盖掉他的改名 —— 这是数据层面的错误行为。

**选择**：

- 运行时只翻译 `system_key IS NOT NULL AND editable = 0` 的两个不可变分类（`TRANSFER`、`UNCLASSIFIED`）。
- 可编辑分类一律按库中原值显示。
- 默认分类的语言在**安装时**决定：自托管者播种时选择语言，之后随时可自行改名。
- 已有实例不做任何改写。

### D8. 报表周期不再携带时区字段 —— 所有者于 2026-09-22 选定

实现任务 2.3 时实测发现：`resolveReportPeriod` 的日期运算**完全不依赖时区**，全部基于 `Date.UTC` 的纯日历字符串算术，函数体内没有任何 `Intl` 或偏移量计算。其返回的 `timeZone` 字段只是附加的元数据标签。进一步检索确认**该字段没有任何消费者**，`REPORT_TIME_ZONE` 也没有 `financial-reporting.ts` 之外的使用者。

**选择**：从 `ResolvedReportPeriod` 与 `resolvedReportPeriodSchema` 中移除 `timeZone` 字段，并移除 `REPORT_TIME_ZONE` 常量。需要展示日历时区的界面直接从配置读取。

**理由**：为了让一个纯函数携带它根本不使用的标签而给它增加必填配置参数，等于把配置耦合进不该耦合的层。该字段既无计算作用也无消费者，属于死重。

**连带收益**：`resolveReportPeriod` 签名不变，因此前端 3 处调用点不受影响，任务 2.3 与 2.4 不再必须捆绑落地。

**备选**：给 `resolveReportPeriod` 增加必填时区参数以保持 API 契约不变（方案 A）。代价是 6 个调用点全部改动，且不能设默认值 —— 任何默认值都会重新引入 spec 明令禁止的"静默回退到 Toronto"。

**契约影响**：报表响应中不再出现 `period.timeZone`。因无消费者，前端与备份格式均不受影响。

### D9. 界面货币选项来自部署声明的账户货币 —— 所有者于 2026-09-23 确认

放开校验后发现契约与界面脱节：API 已接受任意两位小数货币，但 `QuickEntryPage`、`SubscriptionForm`、`MonthlyBudgets`、`TransactionsPage` 的下拉框仍然只列 CAD 和 USD。

**所有者指出的领域前提纠正了本项的设计依据**：账本记录的是银行流水，而流水中的跨境消费已由发卡行换算完毕 —— 加拿大用户在巴黎刷卡，账单上是 CAD。因此"支持 EUR"对该用户没有使用场景。真正需要多币种的情形是**账户本身以不同货币计价**，这正是本账本同时存在 CAD 与 USD 的原因（RBC 导出含 `CAD$` 与 `USD$` 两列）。

由此：

```
货币集合 = 本实例账户所计价的货币   通常 1–2 个，部署时已知且长期稳定
        ≠ 所在地区的流通货币
        ≠ ISO 4217 全集
```

**选择**：新增编译期配置 `VITE_LEDGER_CURRENCIES`，默认 `CAD,USD`，界面下拉框只列出其中的货币。每个值仍经 `ledgerCurrencySchema` 校验，非法值启动即失败。

**已放弃的备选**：完整货币选择器（与实际使用场景不符，且把 1–2 项的选择埋进上百项列表）；自由文本输入（易输错，失去可发现性）；由既有数据推导（首次安装时为空）。

**货币与语言不合并为单一 locale 配置**：两者性质不同 —— 语言属于观看者，可按设备切换；货币属于数据，由账户决定，部署后基本不变。合并会导致"切换界面语言同时改变记账货币"这一错误行为。所有者所说的"semi 绑定"理解为默认值可相关、机制须分离。

**已知局限**：货币严格来说是账户的属性，而当前数据模型中 `accountLabel` 是自由文本，没有可承载该属性的账户实体（`accounts` 表属银行同步时代遗留，手动记账不使用）。全局列表是现有模型下的务实选择；真正的按账户货币需先引入账户模型，不在本变更范围内。

**校验仍独立存在**：下拉框限制的是录入便利性，`ledgerCurrencySchema` 限制的是存储安全。CSV 导入与 API 写入不经过下拉框，因此两层都必须保留。

### D7. 文档分家

`docs/free-preview-deployment.md` 保留为所有者运维记录（含版本 ID、发布证据、授权条款），新增 `docs/self-hosting.md` 作为安装指南，两者互不引用对方的专有内容。安装指南须显式说明 Cloudflare Access 是**必需前置**而非可选项 —— 没有它应用完全裸奔，因为 Worker 只验 Access JWT，不存在回退鉴权。

## Risks / Trade-offs

- **时区改造触及日期边界，回归面最大** → 时区是月份归属、订阅到期、分析区间的唯一依据。改动集中在 domain 层后以 Toronto 与另一时区双参数跑既有测试，确保 Toronto 下逐位不变。
- **434 行字符串抽取是机械但高频的改动，易漏** → 抽取完成后加一条阻断式检查（lint 规则或测试）禁止 `apps/web/src` 的 JSX 与用户可见字符串中再出现汉字字面量，防止回潮。
- **i18n 自建方案将来可能不够用**（复数、性数、RTL）→ 当前两种语言均无复杂复数规则；接口设计成 `t(key)` 形态，日后替换为库时调用点不变。
- **黑名单放行虚构货币代码** → 影响限于所有者自己的报表分桶，可自行修正；不产生金额错误。
- **仓库已经是公开状态且当前无许可证**（实测 `visibility: PUBLIC`、`licenseInfo: null`、forks 0、stars 0）→ 现状等同"保留所有权利"：他人可读但无权 fork 或部署，自托管目标在法律上尚未成立。补加 `LICENSE` 是纯增量操作，不存在需要收回的既有授权，应优先于其余任务完成。
- **生产 D1 标识与 Worker 版本号已经公开可见** → 本变更把 `database_id` 换成占位符并剥离运维记录，可阻止**将来**的提交再携带这些值；历史提交中的旧值已无法通过重写彻底清除（GitHub 对已公开仓库保留孤立提交，按 SHA 仍可访问）。这些值是资源标识而非凭证，单独持有无法使用，真实风险面是 Cloudflare API token 而非该 ID。列入 Open Questions。

## Migration Plan

现有所有者实例视为"配置为 `America/Toronto` + `CAD`/`USD` + 中文"的一个自托管实例，全部默认值与当前行为一致，因此：

- 无数据库迁移。
- 无备份格式版本变更，既有备份继续可恢复。
- 所有者实例的 `wrangler.jsonc` 在本地填回真实 `database_id`（该值不再进仓库）。

部署与公开仓库均不在本变更范围内，需另行授权。回滚即回退应用版本；由于无 schema 变更与无版本号变更，回滚不涉及数据处理。

## Open Questions

1. ~~**许可证选哪个？**~~ **已解决**：MIT，所有者 2026-09-21 确认。见 D1。
2. **是否为抹除生产 `database_id` 与 Worker version ID 而删库重建？** 仓库已公开，重写历史无法彻底清除旧对象，唯一可靠方式是新建仓库并丢弃现有链接、PR 与历史。当前建议**不做**：这些值是资源标识而非凭证。所有者未表态，本变更不依赖该决定，任务 1.2 独立地阻止将来的提交携带该值。
3. **`README.md` 与 `docs/self-hosting.md` 用什么语言？** 界面做了中英双语，但文档目前全中文。安装指南的受众是任意语言使用者 —— 建议指南用英文、README 中英并列，但这会扩大文档工作量，需确认。
4. **默认分类播种语言的交付形态**：是提供两份 seed SQL，还是让安装者在首次登录后自行改名？前者更省事，后者零新增机制。倾向后者，待确认。
